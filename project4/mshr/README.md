# 第二项研究：新 L2 的缺失并发能力（MSHR）

## 实验控制

沿用第一阶段容量研究的最佳三级配置：64 TM、每 8 TM 共享一个 512 KiB L2、16 MiB 全局 L3、L3 延迟 480 周期。Sponza 512×512、同一份 RISC-V ELF、冷缓存启动。

**唯一实验变量：每个新 L2 的 `num_mshr` = 192、384、768。** 每个新 L2 只有一个 slice，8 个 L2 合计分别有 1,536、3,072、6,144 个 MSHR。

以下全部保持不变：
- L1/L2/L3 容量、延迟、相联度、bank/slice 数量及连接方式；
- L2 的 `num_subentries=4`（单个缺失请求可合并的等待者数）；
- L3 的 `num_mshr=192` **每 slice**，全局仍为 8 分区 × 4 slices × 192 = 6,144；
- 时钟、DRAM、kernel、场景及 framebuffer。

实现仅为 `src/arches-v2/main.cpp` 添加 `P4_L2_MSHRS`，在复制 L3 配置**之后**设置新 L2 的 MSHR 数，避免意外改变 L3。另打印这两级的 MSHR 配置供审计。第一阶段的 A/B/C 和容量 case 名称仍固定使用 192，不受源码当前默认值影响。

## 实测结果

| 每个新 L2 的 MSHR | 总 MSHR | 执行周期 | 模拟帧时间 | 相对 192 加速 | L2 命中率 | DRAM 读取 |
|---|---:|---:|---:|---:|---:|---:|
| 192 | 1,536 | 2,193,053 | 1.447560 ms | 1.0000× | 39.389% | 17.155 MiB |
| 384 | 3,072 | 1,140,945 | 0.753099 ms | 1.9221× | 39.165% | 17.150 MiB |
| 768 | 6,144 | **951,937** | **0.628341 ms** | **2.3038×** | 38.704% | 17.154 MiB |

768 相对 192 耗时减少 **56.59%**；384 → 768 继续加速 **19.86%**，开始出现明显的边际收益递减。

相对教程 C（4 MiB L3、192 MSHR），当前最佳组合（16 MiB L3、768 MSHR）加速 **2.4186×**。这个组合比较同时包含第一阶段的容量变化，**不能全部归因于 MSHR**。本次单变量 MSHR 收益应使用表中的 192 基准。

原始两级缓存 B 为 521,272 周期，因此当前最佳三级方案仍需 B 的 **1.8262 倍**时间，尚未超过 B。

## 解释：之前的瓶颈判断得到了实验支持

- DRAM 读取量几乎不变，L3 命中率约 91.43%–91.48%。此次提速不是靠减少大量 DRAM 请求。
- L2 的普通命中率略降而不是上升；half-miss 合并率从 0.371% 增至 1.424%。更大的在途窗口改变了请求/返回时序及合并机会，即使容量和工作负载不变，缓存计数也不必完全相同。
- L2 的 `MSHR Stalls` 从 54,071,109 降到 14,723,759（减少 72.77%），L1 同类阻塞从 6,632,639 降到 2,355,219。
- L2 下级缺失请求速率从约 **3.01 → 5.77 → 6.91 个/周期**，说明更多等待请求能够并行在途。

这些单变量结果强烈支持“教程新增 L2 的缺失并发窗口过小，是当前工作负载下的重要瓶颈”。但 `MSHR Stalls` 还计入返回队列、缺失队列的反压，不能声称它直接测量了 MSHR 满占用周期。

### 为什么 768 不再接近翻倍加速？

实现中每个新 L2 的单 slice 缺失路径每周期最多处理/向下发送一个请求，8 个模块的理论合计上限为每周期 8 个（还有绕过写等流量共享发送路径）。768 配置的 L2 缺失请求速率已达约 6.91/周期。这个限制及其他访存资源可能逐渐接替 MSHR 窗口成为瓶颈；本次未改变发送端口、slice 数等，不能仅凭该数字断言唯一后续瓶颈。

MSHR 扩大需要真实硬件存储、查找和控制资源。模型没有相应面积/功耗/时序成本校准，因此不能把结果解释为“免费增加 MSHR”。

## 校验

- 新跑的 192 配置，**全部已记录性能计数与第一阶段 16 MiB/480 周期结果完全一致**。
- 三种配置的源码只有 `P4_L2_MSHRS` 宏值不同；`analyze.py` 逐字验证。
- 所有图像与第一阶段逐像素一致、全不透明；总射线数均为 777,304。
- 768 最佳配置另做冷启动复跑，检查周期、全部已记录性能计数和像素严格一致；结果写入 `summary.json` 的 `repeat_checks`。
- 第一阶段 CPU 软件参考的 **3/262,144 个像素差异**仍存在，明确保留，不声称独立参考位精确通过。

## 文件与复现

在 `/root/arches` 工作目录内，通过 **tmux** 运行：

```bash
uv run --with pillow python project4/run.py --results /tmp/project4-mshr \
  --cases l2-mshr192 l2-mshr384 l2-mshr768
uv run --with pillow python project4/run.py --results /tmp/project4-mshr-repeat \
  --cases l2-mshr768
# 检验仓库内已存档的数据并重新生成本目录汇总：
uv run --with pillow python project4/mshr/analyze.py
```

`results/` 保存三次正式运行，`repeat/` 保存最佳配置复跑；每次包含原始日志、PNG、完整模拟器源码、构建日志及命令/哈希元数据。`summary.json/csv/md` 为机器可读数据和汇总。

第一阶段 `../results/`、`../summary.*` 和 `../findings.md` 保持为历史证据，不覆写。`../submission/main.cpp`、`../submission/trax_log_my_best.txt` 更新为本轮最佳三级配置；A/B/C 三份提交日志不变。最终 PDF 报告仍未制作。
