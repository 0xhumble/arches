# 最终选定的自主优化：C + 384 MSHR

> 提交用和工作目录中的 `main.cpp` 已移除实验宏、两级/三级切换、额外诊断输出及无关清理，仅保留课程要求和 384 MSHR 优化。按用户指示，清理后**未重新编译或运行**，已有日志保持原样。实际产生日志的完整源码仍在 `results/c-mshr384/main.cpp`；下面的宏实验脚本需要该存档源码，不适用于清理后的固定配置源码。

按用户决定，最终方案只在 PDF Part C 的基础上，把**每个新 L2 的 `num_mshr` 从 192 增加到 384**。不采用探索阶段的 L3 扩容或 768-MSHR 方案。

## 固定配置

- 64 TM，每个 TM 的线程/TP、L1 配置与 C 相同。
- 8 个组内 L2，每个服务 8 TM，容量 512 KiB、1 slice、4 banks、延迟 160 周期。
- L2 的 `num_subentries=4` 保持不变。
- **L3 总容量仍为 4 MiB，延迟仍为 480 周期**，每 slice 192 个 MSHR 不变。
- Crossbar、DRAM、时钟、场景 Sponza、512×512、kernel ELF、冷缓存条件均不变。

这里的 384 是每个 L2 的 MSHR 数；每个 L2 只有一个 slice，8 个 L2 共 3,072 个 MSHR。赋值位于原配置复制给 L3 之后，因此没有顺带增加 L3 的 MSHR。

## 实测结果

| 配置 | 执行周期 | 模拟帧时间 | L2 MSHR Stalls |
|---|---:|---:|---:|
| C：192 MSHR/L2 | 2,302,386 | 1.519727 ms | 57,419,578 |
| 最终方案：384 MSHR/L2 | **1,223,485** | **0.807581 ms** | **23,603,232** |

相对 C **加速 1.8818 倍，耗时减少 46.86%**。

两者 DRAM 读取分别为 68,302,944 和 68,276,352 字节，几乎相同；L2 普通命中率约 39.47% 和 39.20%。增加 MSHR 的主要收益是允许更多 L2 缺失请求同时等待下一级返回，减轻反压，而不是提高命中率或增加数据缓存容量。

`MSHR Stalls` 包含缺失/返回队列阻塞，不能当作 MSHR 表满周期的精确计数。模型没有校准增加 MSHR 的真实面积/功耗成本。

这个结果来自 **4 MiB L3 的单独正式运行**，没有挪用前一轮 16 MiB L3 的 MSHR 实验。它满足对 C 做性能优化的目标，但不是全部探索中的最快方案，也未超过原始两级缓存 B。用户选择较小、单变量的改动作为最终自主优化，不再继续调参。
