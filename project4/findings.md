# Project 4 阶段结论：规定实验 + L3 容量研究

> 以下为第一阶段历史结论。最终提交方案已按用户选择改为 **C（4 MiB L3）仅增加新 L2 MSHR 到 384**，见 [selected/README.md](selected/README.md)。本文当时的“最佳”和提交文件描述不代表当前最终选定方案。

## 1. 实验边界

统一使用 Sponza、512×512、1 SPP、最多三段射线、固定随机种子和相同 ELF。正式运行全部冷缓存启动。除 TM 数量、是否添加 L3、L3 容量/延迟外，不改变硬件参数；没有开展 MSHR、共享范围等后续优化。

完整数值在 [summary.md](summary.md)、[summary.csv](summary.csv) 和 [summary.json](summary.json)，原始日志与各次 `main.cpp` 在 `results/`。

## 2. A/B：8 → 64 TM

- A：2,486,319 周期，1.641135 ms。
- B：521,272 周期，0.344074 ms。
- 加速 **4.7697 倍**，不是计算资源数量的 8 倍。

每 TM 的配置不变，但总 L1、RT core 和线程资源随 TM 数一起增加，因此不能把全部收益归因于算术核心。DRAM 读取量从 62.755 MiB 略升至 64.415 MiB；更多并发并没有等比例减少访存等待和资源竞争。

## 3. B/C：照教程增加三级缓存，反而更慢

C 为 2,302,386 周期、1.519727 ms，耗时是 B 的 **4.4169 倍**。两者均为 64 TM。

| L2 指标 | B：全局共享 | C：每 8 TM 一组 |
|---|---:|---:|
| Hit | 80.2819% | 39.4689% |
| Half miss | 0.4129% | 0.3616% |
| Miss | 19.3052% | 60.1696% |
| 日志中的 MSHR Stalls | 200,115 | 57,419,578 |

`Half miss` 是合并到已在途缺失的请求，并不是普通命中。表中比率由全体模块的计数求和后计算，排除绕过缓存的写请求。

B 的 4 MiB L2 可以服务全部 TM；C 虽然 L2 总容量同样为 4 MiB，但每组只能使用自己的 512 KiB，跨组数据可能重复缓存。新的 L2 未命中还必须访问 480 周期的 L3。这个工作负载下，局部 L2 命中率明显下降，排队/反压增加，而 DRAM 读取量反而从 64.415 增至 65.139 MiB。

这说明增加缓存层次本身不保证加速。阻塞计数包含队列反压，不应直接当作“MSHR 表满的精确周期数”。

## 4. 第一项研究：增大 L3

固定 C 的全部其他参数，L3 延迟保持 480 周期：

| L3 总容量 | 周期 | 相对 C 加速 | DRAM 读取 | L3 命中率 |
|---|---:|---:|---:|---:|
| 4 MiB | 2,302,386 | 1.0000× | 65.139 MiB | 67.6192% |
| 8 MiB | 2,230,102 | 1.0324× | 32.463 MiB | 83.8735% |
| 16 MiB | 2,193,053 | 1.0499× | 17.155 MiB | 91.4812% |

16 MiB 相对 C 的吞吐提高 **4.9854%**，耗时减少 **4.7487%**。DRAM 读取量减少 **73.6646%**，但性能收益远小于流量下降幅度。

**容量确实有用，但不是这个三级结构的主要限制。** 这不能推广为“3D V-Cache 无效”；这里只验证了这个场景、冷缓存单帧和教程指定拓扑/延迟下的容量收益，没有模拟真实堆叠器件。

### 一个有依据、但仍需下一项实验验证的解释

新增 L2 每组只有一个 slice、192 个 MSHR，8 组共 1,536 个；原全局 L2 是 8 分区 × 4 slices × 192 = 6,144 个。新增层级将来自 L1 的缺失流量先限制在更小的并发窗口内。

只考虑 480 周期 L3 访问延迟，用 Little's law 作粗略估计，新 L2 在途窗口支持的持续下级请求速率约受限于：

```
1536 / 480 = 3.2 个请求/周期
```

16 MiB 实测为 `6,604,865 / 2,193,053 ≈ 3.012` 个 L2 缺失请求/周期，已接近这一粗略上限。加大容量可以避免访问 DRAM，但不能消除对 L3 的约 660 万次访问，也不会增加新 L2 的在途窗口。此估计不是完整瓶颈证明，但与高阻塞计数和有限加速一致。

## 5. 延迟敏感性

对 16 MiB 方案额外测试 L3 延迟 528、576 周期，即假设容量扩张带来 +10%/+20% 延迟；这些不是 AMD 硬件测量值。

| 16 MiB L3 延迟 | 执行周期 | 相对 C 的耗时变化 | DRAM 读取 |
|---|---:|---:|---:|
| 480 周期 | 2,193,053 | −4.7487% | 17.155 MiB |
| 528 周期（+10%） | 2,414,834 | +4.8840% | 17.150 MiB |
| 576 周期（+20%） | 2,604,158 | +13.1069% | 17.153 MiB |

只增加 10% 的 L3 延迟，就已抵消本次容量扩张的全部收益。各延迟下 L3 命中率均约 91.48%，DRAM 读取量几乎相同，执行周期却明显增加，进一步支持“容量以外的访问延迟/并发窗口限制很重要”的解释。

## 6. 当前最佳的含义

- **本次三级结构研究中最佳**：64 TM、组内 L2、16 MiB L3、480 周期 L3 延迟。
- **全部实验中最快**：B，64 TM 的原始两级缓存。
- `submission/trax_log_my_best.txt` 与 `submission/main.cpp` 对应前者，符合“优化新三级架构”的范围，不冒称它比 B 快。

下一轮更有依据的方向是检查新 L2 的缺失并发容量，而不是继续盲目增大 L3。本阶段未进行这项调优。

## 7. 校验与限制

所有正式硬件配置的 PNG 必须逐像素完全一致、没有透明未写入像素；都追踪 777,304 条射线。16 MiB/480 周期配置另做冷启动重复运行，复现情况在 `validation/checks.json`。

CPU 软件遍历参考也追踪 777,304 条射线，但与模拟器图像有 **3 / 262,144 个像素差异**，不能声称独立参考位精确通过。不同遍历/数值路径是可能因素，尚未把这三个差异逐项归因；其坐标和参考图均保留在 `validation/`。这不影响已验证的各硬件配置之间严格图像一致性，但限制了独立功能正确性验证的结论。

未校准面积、功耗、真实 3D 堆叠成本，也没有跨场景测试；不从本次单场景结果推导普遍硬件优劣。
